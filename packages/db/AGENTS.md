# packages/db — agent rules

Read this when you change Mongoose schemas, indexes, migrations, the seed dataset, MongoDB users or `@revamp/db` transactions. The root [AGENTS.md](../../AGENTS.md) applies too; this file adds the rules for this area.

## MongoDB users and demo data

* MongoDB users (REV-198): local MongoDB runs with access control as the single-node replica set `rs0`. `startInfrastructure` (setup, dev and `npm run docker:up`, never plain `docker compose up`) generates the `MONGO_*_PASSWORD` values into `.env` (`ensureMongoSecrets`), moves the old default `MONGODB_URI` to `revamp_app`, then runs `scripts/mongo/ensure-ready.js` in the container (`ensureMongoReady`: initiates `rs0`, creates or updates `revamp_app` readWrite, `revamp_read` read, `revamp_admin` dbAdmin + userAdmin on `revamp`; passwords travel in the environment, never in argv). The app, migrations and backfills run as `revamp_app`; never connect the app as root or an Atlas admin. `npm run db:check-roles` checks the rights live. Log a MongoDB URI only through `redactMongoUri` (`@revamp/db`). The shared `revamp-mongo` container serves other sessions too: verify Mongo changes on a separate compose project (other container names and ports), not on it. A new worktree copies `MONGODB_URI` and the `MONGO_*_PASSWORD` lines from the main checkout's `.env` (fresh passwords would not match the existing users). Production (Atlas) gives the same roles on the database in its `MONGODB_URI` (`revamp_prod`), with no `userAdmin` and no root user.
* Demo data (REV-199): `npm run db:seed` loads the fixed dataset of `buildDemoDataset` (`packages/db/src/seed/demo-dataset.ts`: ten `demo-seed` leads in the main statuses with their audits, MVPs, campaigns and events, every address on `.test`) through `seedDemoDataset` (one transaction, fixed `5eed…` ids, never touching another document; `-- --reset` restores the seed documents and removes every other document of a demo lead) after uploading the MVP pages to MinIO; `assertLocalSeedTarget` refuses production and non-local hosts. The demo studio has the sender `Demo Studio <hello@demo-studio.test>` and every sent campaign is `deliveryMode: 'SIMULATED'` with an `outbox` built by `renderOutreachMessage` (REV-221). A new status or required field goes into the dataset too, and `demo-dataset.spec.ts` checks it against the Mongoose and Zod schemas. `npm run db:dump` / `db:restore -- <file> [--drop]` export and import the database with the MongoDB tools inside the container (`scripts/db-archive.ts`; a URI not on port 27017 needs `MONGO_CONTAINER`, so a check stack is never confused with the shared `revamp-mongo`). Seed data is test data: never read it from runtime code (REV-45). The workers' startup recovery (`recoverStalledAuditedLeads`, `apps/workers/src/services/stalled-lead-recovery.ts`) queues MVP generation only for leads matching `stalledAuditedLeadFilter` (`@revamp/db`): `AUDITED` and not tagged `DEMO_SEED_TAG` (REV-204). The tag, not `.test` domains, is the rule, because only the seed writes it; no other automatic job reads existing leads today; a new one must skip the tag the same way. The repair, backfill and migrate scripts, which an operator runs by hand, still cover demo leads.

## Schemas, indexes and validation (REV-48)

* A lead has at most one `MvpProject` and one `EmailCampaign`, enforced by a unique `leadId` index (REV-201). Write them with an upsert filtered on `{ leadId }` and keep `leadId` out of the update body: the upsert copies it from the filter, and MongoDB then retries a concurrent insert as an update. A database made before REV-201 needs `npm run migrate:unique-lead-children --workspace=@revamp/api` (dry run, then `-- --apply`); `checkLeadChildIndexes` (`@revamp/db`) warns at API and worker startup until it ran. A new unique index on existing data gets the same treatment: a dry-run migration that removes duplicates and rebuilds the index, because Mongoose's autoIndex cannot change an index that already exists.
* A `Schema.Types.Mixed` field is validated with its Zod schema from `@revamp/validation` where its value is built, before it is written (REV-200): `SiteComplexitySchema`, `SiteEraSchema`, `ExtractedContactsSchema` and `SiteContentSchema` (the brand extractor drops an invalid optional field with a warning instead of failing the audit), `MvpThemeSchema` (in `checkMvpPage`), `MvpGroundingFlagSchema`, `MvpPageVersionSchema` (`pageVersionEntry`), `MvpRenderFailureSchema` (an invalid `generationFailure` is left out, the reset still runs), `MvpStandardsSchema`, `MvpPerformanceSchema`, `MvpCompletenessReportSchema`, `UpdateMvpTokensSchema`. Only `Audit.axeViolations` (raw axe-core output) and `AnalyticsEvent.metadata` are free-form. A new Mixed field gets a schema and a row in the data dictionary (`../Revamp-docs/database-expertise.md` §4.6); a new field of any kind goes into the dictionary too, and `npm run docs:check-dictionary` lists the fields it misses.
* `Lead.outreachError` (REV-226) is a typed subdocument, not Mixed: the caller builds it and parses it with `LeadOutreachErrorSchema` (the email worker), and `revertOutreachApproval` writes it with the model validators on (`runValidators`), so an unknown code or an over-long message writes nothing. `approveOutreachWithCampaign` clears it. `@revamp/db` still does not depend on `@revamp/validation`.
* Tests that need a real MongoDB (unique indexes, transactions) go in `packages/db/src/__tests__/real-mongo.spec.ts`, which starts one `startMongoReplSet()` server (`packages/db/src/testing/mongo-memory.ts`, `mongodb-memory-server`, binary pinned in the root `package.json` and cached in CI) for all of them. Don't start another server in a new file: parallel `mongod` start-ups slow the Chromium tests enough to break their timing.

The transactions `addLeadToBusiness` and `approveOutreachWithCampaign` live here; how the API uses them and reverts on a failed enqueue is in [apps/api/AGENTS.md](../../apps/api/AGENTS.md).

## Accounts (REV-206)

* `organizations`, `users` and `memberships` are the account collections: a unique `users.email` (lowercase) and a unique `{ userId, organizationId }` on memberships. `createOrganizationWithOwner` writes an organization, its first user and the owner membership in one transaction. Password hashing (`hashPassword`, `verifyPassword`, `hashPasswordWithSalt`) lives here so the API and the seed share one format (`scrypt$<salt>$<key>`); a hash is never logged or returned.
* Invitations and members (REV-207, `organization-members.ts`): `Invitation` stores only the SHA-256 of its token (`tokenHash`, unique) and `expiresAt` (7 days); every function that changes data runs in one transaction. `changeMemberRole` and `removeMember` first write the organization document (`lockMembers`), so two concurrent changes conflict and the second re-reads the owner count: that is what keeps the last owner from being demoted or removed by two racing requests (a real-MongoDB test proves it; do not remove the lock). `createInvitation` takes the same lock, so two invitations for one address cannot both stay pending. A claim of an invitation re-checks usable, unrevoked and unexpired in its own filter. `OrganizationError` carries the rule that was not met; the API maps it.
* The demo dataset has one studio, `Demo Studio`, with an owner `DEMO_OWNER_EMAIL`, an operator `DEMO_OPERATOR_EMAIL` and a viewer `DEMO_VIEWER_EMAIL`, all with `DEMO_OWNER_PASSWORD` (a fixed salt keeps the seed idempotent). It is a local test account; `assertLocalSeedTarget` keeps it out of production. `--reset` deletes these seed accounts by id and nothing else, so real users survive it.

## Business and lead (REV-208)

* `Business` is the company and its site: one per canonical domain (`domain` unique), shared by every studio. A `Lead` is one studio's pursuit of it: `tenantId` (the organization) and `businessId`, with a partial unique index `{ tenantId, businessId }` (only where both are ObjectIds, so leads made before the split are not restricted). The lead keeps copies of the identity fields; audits keep `leadId` (the lead that ran them) and gain `businessId`.
* `addLeadToBusiness` writes the business with an upsert filtered on `{ domain }` (retried once on E11000), then the lead and either its own QUEUED audit or, when the business has a COMPLETED audit, the lead as `AUDITED` with the fields `deriveFromAudit` returns (the API passes `leadFieldsFromAudit` from `@revamp/validation`; `@revamp/db` does not depend on it). `LeadAlreadyExistsError` carries the existing lead's id. Creating a lead with a status is not a transition: `LEAD_TRANSITIONS` governs every later write.
* `findAuditForLead(lead, { completedOnly })` is the one way to read a lead's audit: its own newest, else the business's newest COMPLETED (only COMPLETED audits are shared, so another studio's retry or failure never changes what a lead shows); `auditBelongsToLead` checks an audit id from a request against the lead and its business.
* `migrateBusinesses` / `checkBusinessLinks` (`business-migration.ts`) backfill and warn; the demo dataset has a business per demo lead and puts its leads in the demo studio.

## Tenant ownership (REV-209)

* `MvpProject`, `EmailCampaign` and `AnalyticsEvent` carry `tenantId` like `Lead` (the studio of their lead), with an index on it; `leads` has `{ tenantId, onePageBrochure, createdAt }` for the studio's list and `{ tenantId, status }` for its filters (checked with `explain` in `real-mongo.spec.ts`). Whatever writes one of the four copies the lead's `tenantId`: `approveOutreachWithCampaign` onto the campaign, the deploy worker onto the project, the audit worker onto its `token_usage` events, the demo seed onto all of them.
* `migrateTenants` / `checkTenantLinks` (`tenant-migration.ts`, `npm run migrate:tenants --workspace=@revamp/api`) give leads without a studio to the named (default: oldest) organization and each child the studio of its lead; an event that names no lead stays in no studio; two leads of one business that would land in one studio (the unique `{ tenantId, businessId }` index) are listed as `conflicts` and `--apply` refuses until the duplicate is resolved. Dry run by default, idempotent, real-MongoDB tests.

## Observability helpers (REV-220)

`src/observability/` holds what the API and the workers share and the dashboard must never bundle, which is why it lives here and not in `@revamp/shared-types`: `configureLogging` (routes `console.*` through one JSON line per call in production, `LOG_FORMAT=json|text`), `MetricsRegistry` (Prometheus text format, no `prom-client`) and `loadFileSecrets` (`NAME_FILE` fills `NAME` from a Docker secret file). A new log field or metric goes through these; do not write JSON by hand or add a metrics dependency. Never log a query string, a token or a connection string (`redactMongoUri`).

## Studio sender and outbox (REV-221)

* `Organization.sender` (`{ name, address }`, address lowercased) is the studio's outreach sender; `EmailCampaign` carries `senderName`, `deliveryMode` (`EMAIL_DELIVERY_MODES`, only `SIMULATED`) and `outbox` (`from`, `to`, `subject`, `html`, `text`, `headers` as a `Map` of strings, no `Mixed` field). The message is rendered by `renderOutreachMessage` in `@revamp/shared-types`, shared by the email worker and the seed, so the demo data matches runtime.

## Contact registry (REV-224)

* `ContactRight` (one studio's right to contact one business, `grantedAt` to `expiresAt`, then a cooldown to `cooldownUntil`), `Business.contactHold` (the current or last right, copied) and `Business.optedOutAt`, plus `SuppressedAddress` (the SHA-256 of an opted-out address, unique) make one registry across all studios. Defaults: right 14 days, cooldown 30 days (`DEFAULT_CONTACT_RIGHT_DAYS`, `DEFAULT_CONTACT_COOLDOWN_DAYS` in `@revamp/shared-types`; the API env `CONTACT_RIGHT_DAYS` / `CONTACT_COOLDOWN_DAYS` overrides them).
* The hold is the one atomic rule: `grantContactRight` (`contact-rights.ts`) writes it with a compare-and-set on the business (no hold, or its cooldown over, and not opted out), so concurrent grants have exactly one winner, then creates the right with the same id. Create a `ContactRight` only through it. It returns `{ granted: true, right }` or `{ granted: false, reason }` (`opted_out`, `held` with `expiresAt`, `cooldown` with `availableAt`, checked in that order; the other studio is never named) and a refusal writes nothing. The cooldown blocks every studio, the former holder included. Pass `session` to run it inside the caller's transaction (an aborted transaction leaves no hold and no right); without one it opens its own.
* Durations come from the caller: `@revamp/db` reads no env. `endContactRight` ends a right early (an opt-out) and starts the cooldown at that time; `findActiveContactRight` reads the active right.
* Addresses are stored only as `hashAddress(email)` (trim, lowercase, SHA-256); that function is the one place that normalizes. Never store or log the address of an opt-out.
* `migrateContactRights` / `checkContactRights` (`contact-rights-migration.ts`, `npm run migrate:contact-rights --workspace=@revamp/api`): the oldest open studio lead of each business without a hold gets a right (closed leads, `REJECTED` and `AUDIT_FAILED`, never keep it; a business with only closed leads stays free) granted at migration time (`source: 'MIGRATION'`, not back-dated), other studios' leads of it are listed as `conflicts` and left unchanged, a business with an `UNSUBSCRIBED` lead gets `optedOutAt` and its address hash and no right. Dry run by default, idempotent; the API and workers warn at startup until it ran.
* The demo dataset has a right and hold per demo business for the demo studio's lead (granted a day ago); the unsubscribed florist is opted out with `flowers@florist.test` suppressed. A plain seed run adds no second right to a business that already has a hold or an opt-out.

## Opt-out (REV-227)

* `recordBusinessOptOut` (`opt-out.ts`) is the one place that writes other studios' leads and campaigns for an opt-out, in one transaction: `Business.optedOutAt` (the first time stays), the `SuppressedAddress` hash of the recipient (only the hash, never the address), `endContactRight` for the active right, every studio's lead of the business to `UNSUBSCRIBED` (+ tag `unsubscribed`) and their not-yet-sent campaigns (`DRAFT`, `NEEDS_APPROVAL`, `APPROVED`, `SCHEDULED`) to `UNSUBSCRIBED`; `SENDING`, `DELIVERED` and `BOUNCED` stay as history. It is idempotent (a repeat completes an interrupted call and reports zeros) and without a `businessId` (a legacy lead) it only suppresses the address.
* `@revamp/db` does not depend on `@revamp/validation`, so the caller passes `unsubscribableStatuses` (`leadStatusesInto('UNSUBSCRIBED')`): the state machine stays the one source. Queued BullMQ jobs are not removed; the email worker's HITL gate aborts them because an `UNSUBSCRIBED` lead cannot move to `SENT`.
* `isAddressSuppressed(email)` and `isBusinessOptedOut(businessId)` are the one read side; approval and the email worker use them. `Lead.outreachError.code` gained `CONTACT_OPTED_OUT`.

## Lots and platform audits (REV-232)

* `Lot` (`lots`) is a platform-owned priced offer of one business and its audit: `businessId`, `auditId`, `niche` and `city` (copied from the business), `priceCents`, `currency`, `band`, `need` and `priceSignals` (a typed subdocument array, no Mixed; the price comes from `priceFromAudit` of `@revamp/validation`, never a model), `status` (`LOT_STATUSES`, default `DRAFT`), `releaseAt`, `withdrawnAt`, `withdrawReason` (`admin` or `claimed_by_studio`) and `live`. `live: true` is set while the status can still change (DRAFT, OPEN, RESERVED) and removed on SOLD and WITHDRAWN; the partial unique index `{ businessId: 1 }` where `live: true` allows one live lot per business, so concurrent `createLot` calls have one winner (`LotError('LOT_ALREADY_LIVE')`, a real-MongoDB test with five calls proves it).
* `createLot` refuses with `LotError('LOT_NOT_ELIGIBLE')` a missing business, one with `optedOutAt`, one whose `contactHold.cooldownUntil` is in the future (held, or cooling down) and one with no `city`. It takes the price from the caller: `@revamp/db` does not depend on `@revamp/validation`.
* `transitionLot(id, to, { allowedFrom, set })` is the only writer of `Lot.status`: one atomic filter on `status: { $in: allowedFrom }`, the caller passes `lotStatusesInto(to)` (or fewer for one route, `LOT_ADMIN_OPENABLE`); `null` means nothing was written. `SOLD`/`WITHDRAWN` unset `live`.
* `Audit.leadId` is optional: a platform audit (`createPlatformAudit`) has `businessId` and no `leadId`. Find it by `_id`, never by a lead. `createPlatformAudit` runs in one transaction with `upsertBusinessByDomain` (the same upsert as `addLeadToBusiness`) and returns a COMPLETED audit of the business or a waiting platform audit (`queued: false`), else creates a QUEUED one (`queued: true`; the caller queues the job). A later `addLeadToBusiness` takes a COMPLETED platform audit like any other (`reused`).
* `addLeadToBusiness` takes `withdrawLots: { statuses }` (the API passes `LOT_CLAIMABLE_BY_STUDIO`, DRAFT and OPEN): when the studio's contact right was claimed, the business's lots in those statuses are withdrawn (`claimed_by_studio`) in the same transaction, so a refused right leaves them untouched; a RESERVED lot is not touched (REV-234). The result reports `withdrawnLots`; never pass it to the studio.
