# apps/workers — agent rules

Read this when you change the workers: audit, site assessment, content and brand extraction, standards and SEO, site era, the MVP page generator, publishing, outreach images, or the BullMQ job handlers. The root [AGENTS.md](../../AGENTS.md) applies too; this file adds the rules for this area.

## Deterministic extraction (strict grounding, §3.2.2 of the root file)

* The pre-assessment of discovered sites (REV-98) follows the same rule: `apps/workers/src/services/site-assessment.service.ts` fetches each home page once and parses it without running scripts. A new sign goes into `SITE_BAD_SIGNS` / `SITE_COMPLEXITY_SIGNS` (`@revamp/shared-types`), `SiteAssessmentSchema`, the detector, its tests and the five locales. A site that cannot be checked gets `outcome: 'failed'` with its reason, never a verdict.
* Every happy-dom window in the workers has no base URL, so HTML goes through `withHtmlDocument` or `withoutPreloadLinks` (`apps/workers/src/services/html-document.ts`, REV-144) before parsing: a relative `<link rel="preload">` (Nuxt's `/_payload.json`) otherwise makes happy-dom throw `Invalid URL` in an async preload, an unhandled rejection that can take the workers down mid-audit.
* The original site's language (REV-25, REV-116) is read by `extractSiteContentInPage` (`site-content.extractor.ts`), most specific source first: `<html lang>`, then `<meta http-equiv="content-language">`, then a deterministic guess from the page text (stop words and letters, en/ru/be/pl/lt only, cookie banners skipped; too little text, Ukrainian letters or no clear winner give no guess). An empty or malformed tag counts as missing. The source is stored as `extractedContent.languageSource` (`SITE_LANGUAGE_SOURCES`: `html` | `meta` | `text`); the MVP falls back to English only when the language is unknown. Never ask a model for the language.
* Web standards and SEO checks (`IStandardsChecks`: HTTPS, viewport, title, meta description, a single h1, favicon, Schema.org, OpenGraph; REV-102, REV-118) are read by `readStandardsInDocument` (`apps/workers/src/services/standards.page.ts`, self-contained, attribute values compared in code because happy-dom has no case-insensitive selectors) and scored by `STANDARDS_POINTS` (`@revamp/shared-types`, `STANDARDS_CHECKS` lists them). The audit runs it in the page (`VitalsService`); every MVP publish runs the same reader on the uploaded HTML (`checkMvpStandards`, `mvp-standards.ts`) and stores `MvpProject.standards` (`MvpStandardsSchema`). The MVP's `https` is HTTPS-readiness (the page loads nothing over plain http, its own tracker aside), because serving it over HTTPS depends on hosting; the dashboard shows it in orange and never lists it as fixed or lost. `metaDescription` and `singleH1` are absent on audits made before REV-118, which the dashboard shows as not checked and does not compare by score. A new check goes into the type, `STANDARDS_CHECKS`, the points table (still summing to 100), the reader, the Audit schema, the dashboard labels in all five locales and their tests.
* The MVP's search and sharing tags (REV-118) are built by `buildMvpSeo` (`apps/workers/src/services/mvp-seo.ts`) from verified data only: the original's meta description (else its first paragraph of at least 50 characters, at most 160), `og:image` (the original's own, else the page's first section background or an image of at least 200 px a side, else the logo), `og:locale` only when the language tag names or implies one region, and a Schema.org `LocalBusiness` from the verified contacts. A tag whose source is missing is left out; no model writes any of it. `finishMvpPage` (`apps/workers/src/services/mvp-page-finish.ts`) writes them into the model's page with `seoHeadTags` (`templates/shared/seo.ts`), replacing any the model wrote.
* Whether the original home page looks dated is read by code too (REV-114): `Audit.siteEra` (`ISiteEra`: `dated`, `score`, `signs`, `contentWidth`) is the weighted sum of `SITE_DATED_SIGNS` (weight 2: `table_layout`, `no_viewport`, `frames`, `flash`, `narrow_fixed`; weight 1: `legacy_tags`, `default_font`, `old_jquery`, `stale_copyright`), dated from `SITE_DATED_THRESHOLD` 3. `readSiteEra` (`apps/workers/src/services/site-era.service.ts`, pure) takes the REV-98 `parseHomePage` signals of the page the audit already loaded plus the facts `collectEraFactsInPage` (`site-era.page.ts`, self-contained, REV-141) measures on the rendered page: `narrow_fixed` is a median content-block width of at most 1000 px at 1440 px with fewer than half of the blocks full-bleed, and `default_font` reads the body font only; facts it cannot collect leave those two signs out. `siteComplexity` is size, not age, and does not count. A new sign goes into `SITE_DATED_SIGNS`, `SiteEraSchema`, `readSiteEra` and its tests; a site that can't be checked gets `Audit.siteEraError`, never a verdict.

## The model-written MVP page (REV-135 – REV-141)

* The MVP is a page the model designs and writes in full (REV-135 – REV-141): the model decides layout, sections, markup and CSS; code keeps the facts. `buildMvpSourceBrief` (`mvp-source-brief.ts`, pure, `MvpSourceBriefSchema`) is the only place that decides what the model reads: business, language, services, the original's copy, brand colors and fonts, logo and images, capped by `MVP_BRIEF_LIMITS`, plus the desktop screenshot, and never a contact value. `MvpPageGenerator` (`mvp-page-generator.ts`, `MVP_PAGE_SYSTEM_PROMPT`, provider `VISION_LLM_PROVIDER`, else `MVP_LLM_PROVIDER`, else the first key, else the CLI; the operator's pick wins) writes the copy from the brief only, reworded lightly, never adding numbers, years, prices, ratings, names or testimonials, and writes contacts and booking only as `MVP_PLACEHOLDERS` (`{{phone}}`, `{{email}}`, `{{address}}`, `{{hours}}`, `{{booking}}`). `checkMvpPage` (`mvp-page-check.ts`) rejects a page by code (`MVP_PAGE_CHECKS`: parse/size over `MVP_PAGE_MAX_BYTES`, scripts and forms, external resources, images outside the brief, unsafe CSS, missing theme variables, unknown or unverified placeholders, literal contacts, not one `<h1>`, wrong `lang`); a rejected answer is retried once with the reasons, then the run ends in `MVP_PAGE_FAILURES` and nothing is published, with no stand-in page. With `MVP_PAGE_SELF_REVIEW` on (off by default, REV-143), `generate` renders the accepted page finished, without the tracker (`pageReviewRenderer`, `mvp-page-review.ts`, full page at 1440 and 390 px), and makes one revision call with the captures (`MVP_PAGE_REVIEW_PROMPT`); the revision passes `checkMvpPage` or the first page is kept, and a failed render or call keeps it too (`MvpPageReview`: `revised` | `unchanged` | `rejected` | `failed`). A change (`change`) is never reviewed. With an operator locale (`OPERATOR_LOCALES`: the request's `operatorLocale`, else `Lead.operatorLocale` stored at Add lead or discovery import, REV-162), the user prompt adds `changesInstruction`: after `</html>` a `===CHANGES===` line and a JSON array of `{ change, reason }` in that language, compared with the original site; an edit gets the current version's list as data and returns it updated. `splitChangesBlock` (`mvp-page-changes.ts`) always splits the block off before `checkMvpPage` (on the marker line, else at the last `</html>`, so a loose marker or trailing text never fails the page), and `readDesignChanges` keeps only entries passing `MvpDesignChangeSchema` (`@revamp/validation`: no digits of any script, placeholders, markup, email addresses or links; `MVP_DESIGN_CHANGE_LIMITS`), at most eight; a bad or missing block never rejects a page and leaves the list out, with no stand-in text. The list is stored on its version only (`IMvpPageVersion.changes`; Restore copies it, palette and fonts make no version), and the current page's list is the last version's. `checkMvpGrounding` (`mvp-grounding.ts`) flags numbers and names the source copy does not contain (`MVP_GROUNDING_KINDS`) for the operator; flags never reject. The page declares `MVP_THEME_VARS` (`--rv-color-*`, `--rv-font-*`) in `:root`, read into `MvpProject.theme`; the operator's colors and fonts (`controls`, `MVP_MIN_CONTRAST`, `MVP_FONT_CHOICES`) override them in a trailing `<style id="rv-controls">` with no model call. `finishMvpPage` (`mvp-page-finish.ts`, pure) runs on every publish: fills the placeholders from verified contacts, writes the SEO tags, the controls, the booking form, the tracker and the preview script. Every generation, change and restore stores the raw page as a version at `v/<slug>/versions/<n>.html` (`MVP_PAGE_VERSION_KINDS`, at most `MVP_MAX_VERSIONS`; `index.html` is overwritten, so the preview URL stays). A new page rule goes into the prompt, `checkMvpPage` with its code in `MVP_PAGE_CHECKS` and the recorded-answer fixtures (`services/__tests__/fixtures/page-gen/`); a new `MVP_PAGE_FAILURES` reason gets its words in all five locales; try a change on real sites with `npx tsx scripts/generate_mvp_page.ts [--self-review] [--record <dir>] [--provider <id>] [--model <id>] <out-dir> <url...>` (read-only: no database, storage or queue).

## Failed measurements and the Before / After banner

* A measurement that failed is never replaced by a stand-in value (REV-100): its value is left out, the total is weighted over the measured pillars, and the failure goes into `Audit.measurementErrors` (`AUDIT_MEASUREMENTS`). The Vision critique's templated fallback counts as such a failure (`design`, REV-101): the template is saved for the operator to read but never scored. `Audit.aiFallbackUsed` also covers MVP copy, so read the `design` measurement error, not that flag, to know the critique is a template.
* The Before / After banner (`ImageService.createComparisonBanner`, attached to outreach) carries measured values only (REV-126): the original's LCP, axe violation count and standards score (`comparableStandardsScore`: only when every check was read), and the published MVP's standards score, read from its HTML before the upload. The MVP's web vitals stay off it, because they are measured on the demo host. A value not measured is left out with nothing in its place, and a missing original screenshot shows "Original screenshot not available", never the MVP.

## Jobs and lead status

* An audit job that BullMQ fails as stalled (its worker kept dying) never reaches the processor's `catch`, so the audit worker's `failed` handler closes it through `handleAuditJobFailed` (`apps/workers/src/workers/audit-failure.ts`, REV-145): the audit becomes `FAILED` and the lead `AUDIT_FAILED` with a readable `auditError`, so the operator can retry. Any other worker that moves a lead into a working status needs the same handling for stalled jobs.
* The deploy worker publishes only over a `GENERATING` lead, because the `SCHEDULED → NEEDS_APPROVAL` edge widens `leadStatusesInto('NEEDS_APPROVAL')` (approval transaction: [apps/api/AGENTS.md](../api/AGENTS.md)).

## Simulated email delivery (REV-221)

* The email worker keeps every gate of a real send (HITL `SCHEDULED`, tenant check, campaign claim, MX pre-check, compliance headers, footer and pixel) and then, instead of handing the message to a provider, records it: `simulateDelivery` (`email.service.ts`, wraps `renderOutreachMessage` from `@revamp/shared-types`, which the demo seed shares) renders the message From the studio's sender, and one write sets the campaign `DELIVERED` with `sentAt`, `senderEmail`, `senderName`, `deliveryMode: 'SIMULATED'` and `outbox`; the lead goes `SENT`. Nothing leaves the platform and there is no email provider, SMTP or API key setting. This is the written REV-45 exception of the root file: it is always labelled, and no log or text may say "delivered to" the recipient.
* The contact right is re-checked at send time (REV-226). The email worker's order is: HITL gate (`canTransition(status, 'SENT')`), campaign, `DELIVERED` short-circuit, studio sender, **right**, MX check, claim, outbox. After the sender check, `requiresContactRight('SENT')` makes it call `findActiveContactRight({ tenantId: <job's checked studio>, businessId: lead.businessId }, now)` (`models/ContactRight.model.ts`); a lead without `businessId`, an expired right and an ended one (opt-out, `endedAt`) all count as no right. Then `revertOutreachApproval(leadId, { outreachError: { code: 'CONTACT_RIGHT_EXPIRED', message, at } })` returns the lead to `NEEDS_APPROVAL` with `Lead.outreachError` (cleared by the next approval) and the job answers `{ success: false, aborted: true, reason }`: nothing is claimed, no outbox is written, no `SENT`. The check sits after the `DELIVERED` short-circuit on purpose: a retried job whose email was already recorded still finishes the lead as `SENT`, since it was recorded while the right was active. Test sends (the email-test worker) need no right.
* The sender is read at send time with `loadStudioSender(tenant)` (the job's checked studio), not taken from the campaign, so a change after approval applies. A studio with no sender (a job queued before this shipped) is returned to review through `revertOutreachApproval` and the job answers `aborted`. A retry of a `DELIVERED` campaign changes neither `outbox` nor `sentAt`. The email-test worker renders the draft with `[Test] ` and no pixel, stores nothing, and fails with `SENDER_NOT_CONFIGURED: …` when the studio has no sender.

## Shared audits (REV-208)

* An audit is computed once per business and read by every studio's lead of it. Read a lead's audit with `findAuditForLead` / `findGenerationAudit` (own newest audit, else the business's COMPLETED one), never `Audit.findOne({ leadId })` for a lead that may have taken another studio's audit, and never take the lead from the audit (`audit.leadId` is the lead that ran it). A COMPLETED audit is **read-only**: write nothing derived from one MVP or lead onto it (the comparison banner lives on the lead and the MVP project, because its URL names that MVP's slug). Only the audit worker writes an audit, and only its own lead's.

## Tenant isolation (REV-210)

* Every queue payload (`IAuditJobData`, `IAiGenerationJobData`, `IDeployJobData`, `IEmailDispatchJobData`, `IEmailTestJobData`, `IMvpPageJobData`) carries `tenantId`. The API sets it from `req.tenant`; a worker that queues the next job passes the payload's own value on (audit → generation → deploy). A new queue or payload needs it too.
* A processor loads its lead (or project) and calls `assertJobTenant(job.data.tenantId, lead)` (`src/tenant.ts`) before the first write; a missing, malformed or mismatched tenant, or a lead with none (before `npm run migrate:tenants`), is an `UnrecoverableError` and nothing is written. Writes and the campaign lookup add the studio with `withTenant(tenant, filter)`. The audit worker claims the lead with the studio in the filter and, when that matches nothing, refuses a lead of another studio instead of running its "no longer waiting" path (which would fail that studio's audit).
* Failure handlers (`handleGenerationFailure`, `markLeadAuditFailed`, `handleAuditJobFailed`) change only the lead of the job's studio and do nothing for a job without a valid one; the shared audit is closed only after a lead of that studio is confirmed. Startup recovery queues only leads that have a studio.
* The email-test job reads no record, so it only checks that the tenant is present. Tests: `src/__tests__/tenant.spec.ts` and the tenant cases in each worker spec.
* Deploy order: run `npm run migrate:tenants` and let the queues drain before starting these workers. A job queued without `tenantId` fails, and its lead is left in the status the API gave it (a Regenerate's GENERATING, an approved SCHEDULED) for the operator to retry by hand; the failure handlers deliberately write nothing for such a job.
