# apps/dashboard — agent rules

Read this when you change the operator dashboard (React, MUI, Zustand, React Query). The root [AGENTS.md](../../AGENTS.md) applies too; this file adds the rules for this area.

## Styling, routes, review and design tools (REV-49)

* Colors, radii, typography and component overrides live in the MUI theme (`apps/dashboard/src/theme/theme.ts`, `TOKENS` for dark and light). Components use theme tokens (`text.secondary`, `warning.soft`, `stage.sent`, `border.subtle`, …), never hard-coded hex or rgba values.
* Pages are routes (`apps/dashboard/src/routes`, REV-76): add a path to `ROUTES` in `routes/paths.ts` and the route to `APP_ROUTES`; open a lead with `useOpenLead` / `LeadLink` (`/leads/:id`). A lead is reviewed in `LeadReview` (`components/leadReview`, REV-77): steps Audit, Prototype, Email, with the email draft held by the review (`useEmailDraft`) and signed by the studio (the sender name, else the organization name, never the platform; the default follows the signer until the operator edits it, REV-223) and approval only in `ReviewActionBar` on the email step; keep it that way rather than adding another approve entry point. The home route `/` is the review queue (`ReviewQueuePage`, REV-79): bucket tabs, a list of the bucket's leads and the selected lead's `LeadReview`; its ordering, selection (the selected lead stays listed while a worker moves it to another bucket, `keepSelectedLead`, REV-86), and quick filters (status and score band, REV-80) live in `utils/reviewQueue.ts`. Keyboard shortcuts (REV-47) are defined only in `SHORTCUTS` (`utils/shortcuts.ts`: key, scope, platform modifier, typing and focus rules, checked for conflicts by its tests) and bound with `useShortcuts`; the `?` overlay (`ShortcutsDialog`) lists the registry, so a new shortcut is a registry entry, its handler and a label in all five locales, never a separate `keydown` listener. An element with a shortcut shows it through `KeyCaps` / `ShortcutTitle` (`components/KeyCaps.tsx`, REV-97) and sets `aria-keyshortcuts` from `ariaKeyShortcuts`; never hard-code a key label. The approve shortcut only calls `ReviewActionBar`'s own approve path. The selected lead opens full screen at `/leads/:id` through `useOpenLead` only (Enter, a focused item, or the header's open-full-screen button passed as `LeadReview` `headerActions`, REV-89). The operator changes a model-designed MVP (one with a `theme`, REV-140) only in the floating Design tools panel (`MvpDesignTools` / `useMvpDesignTools`, REV-88), shared by the Prototype step and the full-window preview at `/leads/:id/preview` (REV-91, outside the app shell): the free-text change (`MvpEditPrompt`), colors (`MvpColorControls`: five roles, brand colors first, text contrast checked live against `MVP_MIN_CONTRAST`), fonts (`MvpFontControl`, `MVP_FONT_CHOICES`), versions with Restore (`MvpVersionList`) and Regenerate; an MVP without a `theme` (previous generator) offers Regenerate only. All three actions go through `useMvpPageMutation` (`POST /mvp/:id/edit`, `PATCH /mvp/:id/tokens`, `POST /mvp/:id/versions/:n/restore`), one at a time, with the answer kept per lead and its words from `pageResultText` (`utils/mvpPage.ts`); a new kind of MVP change goes through that path. The preview's version comes from `mvpPreviewVersion` (generation or last change). The Prototype step lists the page's grounding flags (`MvpGroundingFlags`, a warning chip with the count on the Prototype tab); "Show in preview" posts `REVAMP_SHOW_TEXT` to the frame, which the published page's own script (`previewScript`, `finishMvpPage`) scrolls to and outlines. "What changed" (`MvpChangeSummary`, `summarizeMvpChanges`) shows measured facts: standards, the original's axe violations, LCP/CLS with the MVP's host, and business data kept; under them, "Design changes" shows the last version's model-written list as stored (REV-162), with a note when the operator's controls override the model's colors or fonts, and nothing when there is no list. The dashboard sends its language as `operatorLocale` with Add lead, discovery import, generate and edit (`apiClient`, read from `useLanguageStore` at call time).
* Tinted status chips come from the theme: pass `color="warning"` etc. to `Chip` instead of styling its background. New color pairs must keep WCAG AA contrast; `theme.spec.ts` checks it.
* MVP previews are embedded only through `<iframe sandbox="allow-scripts allow-same-origin">` (root §3.2.3). The one other frame is the simulated email in `OutboxDialog` (REV-221): `sandbox=""` (no permissions), a `srcDoc` with a CSP that loads nothing (`outboxSrcDoc`, `utils/outboxFrame.ts`) and `<base target="_blank">`, so the open pixel never loads and viewing it is never an open or a click; keep it that way.
* How the dashboard shows standards results (the MVP's `https` in orange and never fixed or lost; `metaDescription` / `singleH1` as not checked on audits before REV-118) is defined with the standards checks in [apps/workers/AGENTS.md](../workers/AGENTS.md).

## Lead statuses in the UI

* The dashboard maps each status to a Kanban column (`LEAD_STATUS_STAGE`) and a review-queue bucket (`LEAD_STATUS_BUCKET`: Needs you, In progress, Outreach, Closed) in `apps/dashboard/src/utils/leadStages.ts`; a new status must get a column, a bucket, a chip color and a label in all five locales.

## API responses

* The dashboard types API responses as `Serialized<T>` of the shared-types entities (`ILead`, `IAudit`, `IMvpProject`; dates arrive as strings) instead of redeclaring server shapes (REV-67). Mappers read only fields the API returns, with no legacy fallbacks, and a record without an id is a malformed response, never given a made-up id.

## Sign-in (REV-206)

* Every page except `/login` and `/register` sits under `RequireAuth` in `APP_ROUTES`; a new page goes inside it. The session (`useAuthStore`: token, user, organization, role) is kept in local storage, and signing out drops the React Query cache so the next user sees none of it.
* Call the API through `authFetch` (`api/client.ts`), never plain `fetch`: it sends the bearer token and signs out on a 401. Only `authApi.register` / `login` use plain `fetch`, because a 401 there is a wrong password. A `src` or `href` the browser loads itself (an iframe, an image) cannot send the header, so its route must be public on the API side, and that is decided in `apps/api/src/routes/index.ts`.
* Labels of the sign-in pages are the `auth` block of all five locales.

## Roles, Team and invitations (REV-207)

* What a role may do comes from `usePermissions()` (`canWrite`, `canManageMembers`); a new write action (a button, a menu entry, a shortcut) checks `canWrite`, and the API stays the gate (403 FORBIDDEN). A viewer sees the review and the preview with the write actions hidden or disabled and a read-only notice.
* The stored role can be stale: `RequireAuth` asks `GET /auth/me` once per sign-in and `authFetch` refreshes after any 403 (`refreshSessionContext`); a removed member's 401 signs them out.
* `/team` (owners only, `RequireOwner`) lists members, changes roles, removes members and creates invitations; the one-time link is shown once, built from the token (`invitePath`). `/invite/:token` is public (`InvitePage`): the invited address is fixed; register, or join with the password of the existing account (`invitationApi.join`, one call, so it works after a removal too), or, signed in with that address, accept.
* Dashboard tests start as a signed-in owner (`vitest.setup.ts`); a test about roles or sign-in sets its own session in its own `beforeEach` or test.

## Studio sender and simulated emails (REV-221)

* The studio sender is edited in Settings (`SenderSection`, owner only; everyone sees it) and read through `useSenderQuery` (`SENDER_QUERY_KEY`). `LeadReview` passes it to `ReviewActionBar`, which disables Approve and Send test and shows a warning (a link to Settings for the owner, "ask the owner" for others) while the studio has none; `SENDER_NOT_CONFIGURED` from the API shows the same text and re-reads the sender.
* Every email the platform "sends" is labelled "Simulated – not delivered" (`email.outbox.simulated`, the `email.approvedSimulated` and `email.testSimulated` messages): never write text that says an email was delivered. "View sent email" (SENT and later) opens `OutboxDialog`. New strings go into all five locales.
