# apps/api — agent rules

Read this when you change the API gateway: routes, services, enqueueing and repair scripts. The root [AGENTS.md](../../AGENTS.md) applies too; this file adds the rules for this area.

## Transactions and enqueueing

* Adding a lead is one transaction (REV-202, REV-208): `addLeadToBusiness` (`@revamp/db`) finds or creates the shared `Business` of the site (one per canonical domain) and inserts the Lead (with the caller's `tenantId`, from `req.auth.organizationId`) and its first Audit together, then `enqueueAuditOrFail` (`apps/api/src/services/audit-enqueue.ts`, used by Add lead, discovery import and Retry audit) queues the job with `AUDIT_ENQUEUE_TIMEOUT_MS` (the Redis connection retries forever). On failure a lead still `QUEUED` moves to `AUDIT_FAILED` (the `QUEUED → AUDIT_FAILED` edge) and the API answers `503 AUDIT_QUEUE_UNAVAILABLE`. Writers into `AUDIT_FAILED` filter on the one status they move from (`QUEUED` there, `AUDITING` in the workers), not on every source in the table, so a stale job never fails a retried lead. `npm run repair:queued-leads --workspace=@revamp/api` (dry run, `-- --apply`) fixes leads stranded before this.
* Business and lead (REV-208): when the business already has a COMPLETED audit the new lead is created `AUDITED` with that audit's score, complexity and contacts (`leadFieldsFromAudit`, the same function the audit worker uses), no audit job is queued and `addAiGenerationJob` is queued instead (if that fails the lead stays `AUDITED`, the operator presses Generate MVP). A studio's second lead for one site is `409 LEAD_ALREADY_EXISTS` with `details.leadId` (discovery import reports it as `existing_lead`). Read a lead's audit with `findAuditForLead` (own newest audit, else the business's COMPLETED one), never with `Audit.findOne({ leadId })`, and resolve the lead for an MVP generation from the request, not from the audit: `POST /mvp/generate` carries `leadId`, `findGenerationAudit(auditId, leadId)` returns the asking lead, and an audit id alone is refused when more than one lead reads the audit (a shared audit's `leadId` is another studio's lead). `GET /mvp/:id` matches an MVP id or a lead id, never an audit id. The reused path's generation queue call has the same 5 s limit as the audit job. Create an Audit with the lead's `businessId`. Leads made before the split get theirs from `npm run migrate:businesses --workspace=@revamp/api` (dry run, `-- --apply`); the API warns at startup until it ran.
* Add lead claims the contact right (REV-225): `LeadService.createLead` passes `contactRight: { durations: { rightDays: CONTACT_RIGHT_DAYS, cooldownDays: CONTACT_COOLDOWN_DAYS }, source: 'ADD_LEAD' }` to `addLeadToBusiness`, which calls `grantContactRight` inside the same transaction as the lead (both the own-audit and the reused-audit path), so a refusal aborts everything: no lead, no audit, no new business. `ContactRightRefusedError` is mapped by `contactRightRefusal` (`lead.service.ts`, also used by the discovery import) to `409 CONTACT_RIGHT_HELD` (`details.expiresAt`), `409 BUSINESS_IN_COOLDOWN` (`details.availableAt`) or `409 BUSINESS_OPTED_OUT`; the body names no other studio, its id or its lead. The studio's own earlier lead is still `LEAD_ALREADY_EXISTS`, checked first. The 201 `data` carries `contactRight: { expiresAt }`. A failed audit enqueue keeps the right: the lead stays as `AUDIT_FAILED` and Retry audit continues it, so reverting the right would leave a live lead without one; only an aborted add leaves no right. Scripts (no `tenantId`) never claim. The discovery import (`discovery.service.ts`) reads the shared `Business` and `SuppressedAddress` through `contactAvailabilityByDomain` (`@revamp/db`, reason and date only) to mark `new` candidates `unavailable` and to report `right_held`, `cooldown` or `opted_out` per candidate without stopping the loop.
* Approving outreach is one transaction too (REV-203): `approveOutreachWithCampaign` (`@revamp/db`) moves the lead `NEEDS_APPROVAL → SCHEDULED` and upserts its campaign together (null, nothing written, when the lead is no longer awaiting approval), then `enqueueEmailOrRevert` (`apps/api/src/services/email-enqueue.ts`, `EMAIL_ENQUEUE_TIMEOUT_MS`, refuses at once while Redis is not `ready`) queues the send. On failure `revertOutreachApproval` moves a lead still `SCHEDULED` back to `NEEDS_APPROVAL` (the `SCHEDULED → NEEDS_APPROVAL` edge) and its `SCHEDULED` campaign to `NEEDS_APPROVAL` without its approval stamps, and the API answers `503 EMAIL_QUEUE_UNAVAILABLE`. Because that edge widens `leadStatusesInto('NEEDS_APPROVAL')`, the deploy worker publishes only over a `GENERATING` lead. `npm run repair:scheduled-leads --workspace=@revamp/api` (dry run, `-- --apply`) fixes leads stranded before this.
* Approval needs an active contact right (REV-226): after the status, `NO_CONTACT_EMAIL` and sender checks and before the transaction, approve reads the studio's right for the lead's business (`activeContactRight(req.tenant, lead.businessId)`, `data/contact-rights.ts`, through `req.tenant.rights`: granted, not expired, not ended; a lead without `businessId` has none) and answers `409 CONTACT_RIGHT_REQUIRED` with `details.expiredAt` (the studio's latest right's `endedAt` or `expiresAt`, absent when it never had one) otherwise; nothing is written and no job is queued. The guard is `requiresContactRight('SCHEDULED')` (`@revamp/validation`, next to `LEAD_TRANSITIONS`); never keep a local status list. The check uses the caller's studio, so a studio's conflicting lead for a business another studio holds (REV-224 migration) is refused. The test send goes to the operator and needs no right. `ContactRight` is tenant-guarded like the other studio-owned models (`tenant-guard.ts`). A send returned to review by the worker carries `Lead.outreachError`; the next approval clears it.
* Studio sender and simulated delivery (REV-221): `Organization.sender` (`{ name, address }`) is set by the owner at `PUT /organization/sender` (`sender.routes.ts`, mounted before `/organization`, owner only, writes `req.auth.organizationId` only, no DELETE) and read by every role at `GET /outreach/sender`. `requireSender` (`sender.service.ts`) answers `409 SENDER_NOT_CONFIGURED` and approve and test send call it first, so a studio without a sender writes nothing and queues no job; the campaign gets `senderEmail` and `senderName` from it at approval (the worker re-reads the sender at send time). No email is delivered: the test send answers `{ to, from, subject, simulated: true }` and `GET /outreach/:id/outbox` returns the message the worker recorded (`req.tenant.campaigns`, another studio's lead is the usual `404 LEAD_NOT_FOUND`, no outbox is `404 OUTBOX_NOT_FOUND`) and writes nothing, so reading it is never an open or a click. This is the REV-45 exception of the root file. There is no email provider setting in the API.

Errors: throw `AppError` with a code from `API_ERROR_CODES`; only `errorHandler` writes error JSON (root §3.2.9). The `@revamp/db` side of these transactions: [packages/db/AGENTS.md](../../packages/db/AGENTS.md).

## Authentication (REV-206)

* Every route needs a session token (`requireAuth`, `middlewares/requireAuth.ts`, JWT HS256, 7 days, `Authorization: Bearer`) except the ones `routes/index.ts` mounts without it: `/health`, `/auth/register`, `/auth/login` (`/auth/me` guards itself), `GET /invitations/:token` and `POST /invitations/:token/join` (`/invitations/:token/accept` guards itself), `/track/*` (called by email recipients and MVP pages, with a campaign token) and `GET /mvp/preview/:slug` (an iframe cannot send a header). `routes/__tests__/route-auth.spec.ts` walks every registered route and lists the public ones by hand, so a new route fails it until you decide: add a guarded route under an existing guarded mount, or name it public there with a reason.
* `requireAuth` verifies the token, then reads the membership from the database on every request and sets `req.auth` (`userId`, `organizationId`, `role`) with the **role from the database**, never from the token (REV-207): a removed member is 401 at once, a changed role applies at once. Nothing filters data by organization yet (REV-209): a signed-in user sees every lead.
* Passwords are hashed with `scrypt` (`hashPassword`, `verifyPassword`, `@revamp/db`); login answers an unknown email and a wrong password with the same `INVALID_CREDENTIALS` after the same hashing work. Registration is `createOrganizationWithOwner` (one transaction); a duplicate email is E11000 from the unique index, mapped to `EMAIL_TAKEN`. `JWT_SECRET` (at least 32 characters) is required.
* Roles (REV-207): `owner` > `operator` > `viewer`; `canWrite` and `canManageMembers` in `@revamp/shared-types` say what each may do. Every non-`GET` request on the guarded mounts passes `requireWriter` (a viewer gets `403 FORBIDDEN`), and `/organization/*` passes `requireOwner`. A new write route goes under an existing mount; `route-auth.spec.ts` walks every route and checks 401 without a token, 403 for a viewer on every write route, owner-only for `/organization/*`, and that public routes are never 401.
* Members and invitations: `organization.service.ts` acts on `req.auth.organizationId` only, never on an organization id from the request. `OrganizationError` codes from `@revamp/db` map to `AppError` in `organization-errors.ts`. An invitation token is returned once at creation and stored as a SHA-256 hash; registering with `invitationToken` joins the invited organization instead of creating one.
* Route tests send a token through `authedRequest` (`routes/__tests__/authed-request.ts`); tests of sign-in itself use plain supertest.


## Tenant scope (REV-209)

* Leads, MVP projects, campaigns and analytics events belong to a studio (`tenantId`). The API reads and writes them only through `req.tenant` (set by `requireAuth`; `scopeFor(tenantId)` in `src/data/tenant-scope.ts`): `req.tenant.leads.findById(id)`, `.mvps`, `.campaigns`, `.events`. Every filter becomes `{ $and: [{ tenantId }, filter] }`, creates and upserts are stamped, and a filter, update or document that names `tenantId` is refused. Never import `Lead`, `MvpProject`, `EmailCampaign` or `AnalyticsEvent` as values outside `src/data/` and `src/scripts/`: `src/__tests__/tenant-guard.spec.ts` fails with the file and line. Services take the scope as their first argument (`LeadService.getLeads(scope, query)`, `findGenerationAudit(scope, …)`, `enqueueAuditOrFail(scope, …)`).
* Another studio's record answers the endpoint's usual 404 (`LEAD_NOT_FOUND`, `MVP_NOT_FOUND`, `AUDIT_NOT_FOUND`, `NO_COMPLETED_AUDIT`, `DISCOVERY_JOB_NOT_FOUND`), never a different answer: the id must not be confirmed. Audits and businesses are shared; an audit is reached through a lead of the caller's studio (`GET /audits/:id` answers only when such a lead reads it).
* Public routes (`/track/*`, `GET /mvp/preview/:slug`) have no studio: they use `bySecret` (campaign by `trackingToken`, MVP by slug or id), then `scopeFor(record.tenantId)` for everything after. A lead id in a request body is never trusted; the lead is the campaign's or the MVP's own. Records without a studio form a legacy bucket reachable only this way.
* A discovery job's data carries `tenantId`; status and import of another studio's (or an ownerless) job answer `DISCOVERY_JOB_NOT_FOUND`. The "already a lead" check is per studio.
* A new route must be added to `TENANT_OWNED`, `PUBLIC_BY_SECRET` or `NO_TENANT_DATA` in `routes/__tests__/tenant-isolation.spec.ts`, and a tenant-owned one needs a wrong-studio test there (real MongoDB, queues mocked). Specs that mock the models use `__tests__/scope-passthrough.ts` for `data/tenant-scope.js`.
* Records made before the studios get theirs from `npm run migrate:tenants --workspace=@revamp/api` (dry run, `-- --apply`, `--organization <id>`); the API and workers warn at startup until it ran.
